# D.I.V.E. 学生手册要点与执行计划

> 手册版本：v1.6（2026-09-21）· 赛诺菲 × 四川大学 · 2026 秋季 ｜ 本文件提炼与本项目执行直接相关的条款，冲突处以项目组通知为准。

## ⚠️ 三个改变前提的关键事实

1. **评测目标是 LongMemEval Oracle 档，不是 S/M 档**。数据文件 `longmemeval_oracle.json`，500 题，**历史已剪至证据会话**（每题的 haystack 只含与答案相关的会话）。考察重点是写入、更新、组织与调用，而非大海捞针式检索。此前 01/06 文档中"115K/500K 长历史、打赢 full-context"的前提**作废**（保留原文仅作背景知识）。
2. **Full-context 被明令禁止**：附录 F.1 投机实现第 2 条——"全量历史拼入上下文，以超长窗口替代记忆机制"显著扣分或判 0 分。GLM 双模型分工依然成立，但理由从"省上下文成本"改为"写入质量与仲裁分级"。
3. **个人赛 + 项目组统一复跑**：Benchmark 得分 = Overall Accuracy × 40，官方 `src/evaluation/evaluate_qa.py` + GPT-4o judge，**以项目组复跑为准，不以自报分为准** → 可复现性是生命线（我们的 `lmem eval run` 已输出兼容 JSONL ✓）。

## 1. 项目基本信息

- **性质**：校企协同工程实践（非实习、无补贴、不认定学分）；9/18 启动，12 月底交付
- **形式**：15 人分 3 组仅用于辅导；**独立实现路径、独立仓库、独立答辩计分**
- **评分（100 分）**：Benchmark 40 ｜ 代码质量 20 ｜ 汇报答辩 15（展示6+问答9）｜ 团队协作与成长 15 ｜ JDI 10
- **双周辅导 6 次**（10/8 起）：出席+进度发言 = 1 分/次；mentor 引导式，**要求携带具体问题、已验证方案、实验结果**参加
- **结业线**：全部交付物 + 总分 ≥ 60 + 辅导出席 ≥ 4/6 且发言

## 4. 必做项差距分析（附录 B）

- **B.1 遗忘与生命周期（缺口⚠️）**：需实现时效衰减 / 访问频率 / 重要性 / 容量上限至少一种策略——当前完全没有，排入 Phase 2 首位；
- **B.1 结构分层（部分缺口）**：建议 Episodic/Semantic/Working 三层——现有 semantic 事实卡；episodic 原文层未实现（与 Mem0 对比的已识别 gap，升级为手册建议项）；working memory = 当前会话上下文窗口（生成端拼装即可）；
- **B.1 更新与冲突**：✅ 版本化失效 + superseded_by 可追溯，已超手册底线（含历史版本保留方式）；

- **B.2 检索增强**：Rerank / Query Rewriting / 时间过滤——时间过滤已有（as-of），rerank 与改写在 roadmap；
- **B.5 日志可追踪**：✅ evidence + citations + gate 动作 + timings 已满足"追踪单次回答依赖的检索过程"；
- **B.5 公开仓库 + 真实 commit 历史**：⬜ **立即 git init 并推 GitHub**，保持真实提交粒度；

## 6. 阶段执行计划

**Phase 1 · Understand & Design（现在 → 11 月上旬，技术方案截止）**
1. 本周：git init + GitHub 建仓（真实 commit 历史）；配 `ZAI_API_KEY` 跑 `lmem probe` 实测模型；
2. 下载 `longmemeval_oracle.json`，`lmem eval run --limit 30` 拿第一组真实数字（含分题型）；
3. 小规模验证（30–50 题）：验证写入→检索→答题闭环，记录 token 成本，形成成本估算表（手册 1.6 要求方案阶段给出 500 题答题 + 官方评判成本）；
4. 写**个人技术方案**（11 月上旬交）：以 research/06 + 本文件为底稿，按交付物模板补架构图、数据模型、四流程、选型理由、已知局限、成本估算；
5. 双周辅导（10/8 首次）携带：方案初稿 + 30 题实验结果 + 具体问题清单。

**Phase 2 · Build & Iterate（10/10 → 11/30）**
1. LLM 抽取替换规则抽取（GLM flash + schema 约束 + 5% 抽样校验）；
2. 补齐必做缺口：遗忘/生命周期策略、episodic 原文层、query rewriting / rerank；
3. 每次辅导带"已验证方案 + 实验结果"；维护技术笔记（协作 15 分素材）。

**Phase 3 · Benchmark & Optimize（11 月下旬 → 12 月上旬）**
1. 全量 500 题统一流水线跑批（官方 JSONL）；分题型失败模式分析，迭代 2–3 轮；
2. 评估报告草稿：配置、Overall Acc、分题型、_abs 拒答题准确率、Task-averaged Acc、token/费用/耗时、失败案例；
3. 冻结配置与阈值（留存调参记录）。

**Phase 4 · Deliver & Defend（12 月中 → 月底）**
- 文档收口、Code freeze（答辩前 3 个工作日）、答辩演练（问答 9 分：预演"为什么这样设计/换模型会怎样/失败案例"）。

## 7. Benchmark 拿分策略（Oracle 档特性推演）

- haystack 只含证据会话 → **信息抽取类题型的胜负手在写入粒度与证据组织**（抽取漏了必错，故 LLM 抽取质量 + 原文层兜底是第一优先级）；
- 知识更新题：版本化失效已具备，是相对优势，稳拿；
- 拒答题（30 题 `_abs`）：门控已就位，重点做"该拒未拒/不该拒误拒"双向调优；
- 多会话推理/时间推理：靠证据齐全度 + 生成端（5.3 路由/仲裁）；
- 所有优化以**官方 evaluate_qa.py 复跑口径**验证，自建 judge 仅做开发期快速反馈。
